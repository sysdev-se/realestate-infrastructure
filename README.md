# realestate-infrastructure

Terraform for the realestate system: everything it runs on in GCP.

## What it creates (per environment)

| Resource | Notes |
|---|---|
| Project `realestate-<env>-NNNNNN` | Inside the `realestate` folder owned by root-infrastructure, linked to billing, no default network. |
| Project APIs | artifactregistry, compute, iam, iamcredentials, run, secretmanager, servicenetworking, sqladmin, storage (servicenetworking and sqladmin are enabled up front for the database that comes later). |
| Artifact Registry `containers` | Images for all realestate apps. Keeps the 10 newest, deletes others after 30 days. |
| Cloud Run `realestate-api` | Public, 1 vCPU / 512Mi, scales 0–2, billed per request. Runs as its own SA `realestate-api`, which can only read its own secrets. Gets `ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET` and `ADMIN_PASSWORD` from Secret Manager, `CORS_ALLOWED_ORIGINS` = both of realestate-web's run.app URLs, and `IMAGE_BUCKET`. |
| Bucket `realestate-<env>-NNNNNN-listing-images` | Listing images uploaded through realestate-api, which alone can read/write/delete them (`storage.objectUser`) and serves them. Private (org policy). **Objects are deleted after ~1 day** (demo data), no soft delete. |
| Secrets `realestate-api-access-token-secret`, `realestate-api-refresh-token-secret`, `realestate-api-admin-password` | realestate-api's JWT signing keys (64 random chars each) and its seeded admin's password (32 chars), `asia-southeast1` only. Generated by Terraform but never stored in state (ephemeral + write-only). See below. |
| SA `deploy-realestate-api` | `sysdev-se/realestate-api` impersonates it via WIF to push images and deploy `realestate-api`. Nothing else. |
| Cloud Run `realestate-web` | Public Nuxt SSR app, 1 vCPU / 512Mi, scales 0–2, billed per request. Runs as its own SA `realestate-web` (no roles). Gets `NUXT_PUBLIC_API_BASE` = the api's deterministic URL (`https://realestate-api-<project number>.<region>.run.app`, computed so the api can read the web's URLs without a cycle). |
| SA `deploy-realestate-web` | `sysdev-se/realestate-web` impersonates it via WIF to push images and deploy `realestate-web`. Nothing else. |

The database and the network come in later changes (parked: `.agents/RE-3/cloud-sql-notes.md`).

## Deploying an app

Terraform creates each Cloud Run service with Google's placeholder image and then
ignores the image: **app repos own the image, this repo owns everything else**
(env vars, scaling, IAM).

The app repo needs these secrets:

| Secret | Value |
|---|---|
| `GCP_WIF_PROVIDER` | same as in this repo |
| `GCP_SERVICE_ACCOUNT` | output `api_deployer_service_account` (realestate-api) or `web_deployer_service_account` (realestate-web) |

Its workflow then pushes to `<output artifact_registry>/<service>:<sha>` and runs
`gcloud run deploy <service> --image <image> --region asia-southeast1 --project realestate-prod-000001`.
Pass only `--image`: any other setting (env vars, memory, labels, ...) would be
reverted by the next `terraform apply`. For the same reason, don't use the
`google-github-actions/deploy-cloudrun` action without `skip_default_labels: true`,
nor `gcloud run deploy --source` or `--allow-unauthenticated` (the deployer may not
use Cloud Build or change IAM).

A new public service's first apply usually fails on the `allUsers` grant ("do not
belong to a permitted customer"): the `allUsersIngress` tag hasn't propagated to the
org policy yet. Re-run the failed job.

## Secrets

`environments/<env>/secrets.tf` generates each secret with an ephemeral `random_password` and
writes it through `secret_data_wo`, so the value is never in state, plans or logs. Nobody
needs to know the JWT keys. The admin password (user `rikard.virta@sysdev.se`) can be read by
the people in `local.admin_password_readers` (folder editors can't read secret values):

```sh
gcloud secrets versions access latest --secret realestate-api-admin-password --project realestate-prod-000001
```

To **rotate** a secret, bump its `version` in `local.api_secrets` and merge. The old
version is destroyed. New instances read the new value; redeploy (or wait for
scale-to-zero) to replace running ones. Rotating a JWT key logs everyone out. A new admin
password applies when the app re-seeds, which today (in-memory DB) is every instance start.

## Layout

```
environments/<env>/   one Terraform root (own project, own state prefix) per environment
modules/              building blocks shared by the environments
```

Only `prod` exists today. To add an environment:

1. `cp -r environments/prod environments/<env>`
2. `environments/<env>/backend.tf`: `prefix = "<env>"`
3. `environments/<env>/terraform.tfvars`: `environment = "<env>"` and a new `project_id`
4. `.github/workflows/terraform.yml`: add `<env>` to `matrix.environment`

## How changes are applied

`.github/workflows/terraform.yml` runs when `environments/**`, `modules/**` or the
workflow itself changes:

- PR to `main`: `fmt -check`, `init`, `validate`, `plan` for every environment.
- Push (merge) to `main`: `terraform apply -auto-approve`.

CI authenticates via WIF as `tf-realestate`, which only has access to the
`realestate` folder and the `sysdev-tfstate-realestate` bucket. Both are created by
root-infrastructure (`bootstrap/systems.tf`).

Repo secrets:

| Secret | Value |
|---|---|
| `GCP_WIF_PROVIDER` | root-infrastructure output `wif_provider_name` |
| `GCP_TF_SERVICE_ACCOUNT` | root-infrastructure output `systems.realestate.terraform_service_account` |

## Running locally

```sh
gcloud auth application-default login \
  --impersonate-service-account=tf-realestate@root-infrastructure-485309.iam.gserviceaccount.com
cd environments/prod && terraform init && terraform plan
```

Impersonating requires `roles/iam.serviceAccountTokenCreator` on `tf-realestate`.
